Under the hood

This page is for anyone who wants to see what NickelOS actually changes. It's also the map for troubleshooting: if something's off, the piece responsible is probably in one of these tables.

The board and the overlay

NickelOS is the ChromiumOS board nickel, which inherits reven. Everything NickelOS adds or changes is in one overlay, and that keeps moving to a new ChromiumOS release manageable:

  • New packages go in the overlay as ebuilds, ours and ported ones.
  • Changes to Google's packages are patch files under patches/<category>/<package>/. A profile hook applies them when the package builds, so Google's code itself stays untouched in the tree.
  • Settings for the board live in its profile: USE flags, the firmware list, kernel options, which of Google's packages are masked.

Beyond the stock board, NickelOS adds:

  • Firmware. The full set for PCs, not just Chromebooks: Wi-Fi, Bluetooth, and Intel, AMD and NVIDIA graphics.
  • Kernel. virtio_blk built in, so NickelOS boots as a VM too.
  • No hardware reporting. reven sends hardware reports to Google, and NickelOS drops that package. It also has its own update ID and identity (NAME=NickelOS in /etc/os-release).

nickel-appd

nickel-appd is the most NickelOS-specific piece, and the one to look at first when an app misbehaves in the launcher or on the shelf. It runs in your session as you (nickel-appd job), inside Chrome's mount namespace, with the session environment, and owns org.nickelos.Apps on the system bus. Only you, the user Chrome runs as, can call it.

Chrome keeps Linux apps in its GuestOS registry, which on a Chromebook is filled from a VM by vm_cicerone. nickel-appd fills it for the device itself, as VM nickel, container host:

WhatHow
Apps in the launcherReads every .desktop file in XDG_DATA_DIRS, copies each icon where Chrome looks first, and sends the list to Chrome. It sends it again whenever apps come or go
Starting appsLaunchApplication(desktop_file_id, args): Chrome asks, nickel-appd starts it with your session environment
The TerminalSpawnShell(terminal, status, command, env): starts your login shell on the terminal the Terminal app hands over, outside Chrome's sandbox
Dark/light mode and accent colourSetAppearance from Chrome, passed on to the portal backend, which tells apps
The file pickerFileSelected: Chrome's answer to the portal backend's file dialog
NotificationsNotificationEvent: clicks, buttons and closing, back to the app
Tray iconsIt's the tray apps register with (org.kde.StatusNotifierWatcher). TrayEvent carries clicks and menu choices back
UninstallingUninstallApplication: through Flatpak, Portage (with pkexec) or by deleting an AppImage
App infoGetAppDetails: version, size, data size for Settings
AutostartStarts ~/.config/autostart and /etc/xdg/autostart entries once per sign-in
LocationThe GeoClue agent: apps get a location only while ChromeOS's location switch allows it. It also asks ChromeOS's network manager (shill) for Wi-Fi scans, since GeoClue may not start them itself
Steam's gamesWrites launcher entries for installed Steam games
PreviewsThumbnail(path, size): previews of what Chrome can't decode, made by sandboxed thumbnailers

It also installs nickel-open, the handler that sends links and files from Linux apps to ChromeOS. Its messages go to the system log: grep nickel-appd /var/log/messages.

ChromiumOS's other packages

PackagePatch
chromeos-login (session_manager)A local account's session runs Chrome as its own user. No hardware overlays on NVIDIA (page flips timed out)
cryptohomeYour home allows programs and symlinks (ChromeOS mounts it noexec, nosymfollow, which breaks AppImages, scripts and Flatpak). A local account owns its own vault
selinux-policycryptohome's namespace mounter may read /etc/passwd (local accounts' users). Files seen through the overlay mounts on /usr and /etc keep their own labels. lsblk may read udev's database
cros-disksMounts belong to the signed-in user. Other systems' partitions are hidden, and Windows' volume opens read-only. Read-only disk mounts are really read-only (ChromeOS's FUSE mounts still wrote to the disk)
crash-reporterA local account's crash reports go into its own encrypted home, where it can write them
chromeos-initThe kernel may start elogind's cgroup release agent, and crash_reporter by its merged-/usr path, so crashes are collected
os_install_serviceThe installer installs to the disk you picked. Its sandbox allows the calls Gentoo's lsblk, cp and lvm make
system_apiA VM type of its own, NICKEL_HOST, for apps on the device
sommelierExplicit sync for X11 apps on NVIDIA. virtio-gpu calls only on virtio-gpu (they froze NVIDIA). ChromeOS's cursors for X11 apps
update_engineDownloadable system parts (handwriting, voices, fonts) from NickelOS's server instead of Google's
minigbmAn nvidia-drm backend on NVIDIA's own buffer allocator. On AMD, it loads ChromiumOS's older AMD driver, which it allocates through, from /usr/lib64/cros/dri, kept apart from Gentoo's Mesa

cras_rust (CRAS)No requests for the noise cancellation model, which only Chromebooks can download

crosh-extensionThe Terminal's home page offers the device, not a Linux VM to set up

spacedIts sandbox lets Gentoo's lvm list devices and check semaphores
screen-capture-utilsscreenshot uses the EGL device of the card it captures (it failed with Gentoo's Mesa on Intel and AMD)
vboot_referencecrossystem doesn't print errors about the Chromebook firmware device a PC doesn't have
chromeos-hangulKorean input in JavaScript (Chrome no longer runs Native Client)
chromeos-kernelNickelOS turns off two of the ChromiumOS security module's mount restrictions so Flatpak's sandbox (bubblewrap) can mount inside user namespaces and through symlinked paths.
